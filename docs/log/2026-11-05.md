# 2026-11-05 (학습) ~ 11-06 오전 (평가·정리)

## 결정
- **학습은 CPU로.** MPS는 11-04에 2 step 만에 Metal 어서션으로 abort(일지 11-04 막힌 것). `--device cpu --max-length 256 --batch 16 --epochs 2`, 변형 2개(confusable 쌍 라벨 0 포함 / 제외) 순차. 7 s/step → 변형당 약 65분(깨어 있을 때).
- **에폭마다 val을 채점해 로그로.** 체크포인트 저장 직후 콜백(`on_save`)이 학습 중인 모델로 train 상위 5건 쌍 1,090 + val 1,288을 채점(3분) — 임계값·질의 지표는 rank ≤ 5만 보므로 train 전체 4,233을 다시 채점할 이유가 없다. 에폭 선택을 로그만 보고 할 수 있다.
- **best 선택 기준은 11-04 그대로** val 목적함수(neg_no_match − false_no_match − dropped_rate) 최대 → `ft_no_confusable_e2`(0.912 > 제로샷 0.895). 제로샷을 포함해 겨루게 했다 — 학습이 제로샷을 못 이기면 학습 안 쓰는 게 맞으니까.
- **two_stage band의 lo = 단일 임계값.** train 점수 분포로 lo를 잡으면(음성 누적 precision 0.95 → 0.861, 양성 5분위 → 0.719) 모델이 train 쌍을 봤기 때문에 lo가 너무 높고 val 양성이 아래로 떨어진다(1차 two_stage positive false no_match **0.404**). hi만 train 분포(위에서부터 양성 precision ≥ 0.95 → 0.9993)로 잡고 lo는 threshold(0.0047). two_stage = "로컬 yes 중 자신 없는 것만 API".
- **리랭커 추론 기본 장치 cpu.** eval_graph `--workers 3`에서 리랭커(MPS)와 bge-m3(MPS)가 다른 스레드에서 겹치자 `failed assertion _status < MTLCommandBufferStatusCommitted` 로 프로세스 사망(제로샷 61/65, 파인튜닝 46/65에서 죽음). 5쌍 0.4s라 CPU로 충분. `RERANKER_DEVICE`로 바꿀 수 있다.
- `best/`에는 추론 파일만(1.1GB). pick이 optimizer.pt 등 2GB를 같이 복사해 디스크가 3.4GB까지 떨어졌다 — pick에 ignore 추가, 체크포인트의 optimizer 상태 삭제(가중치는 유지, 12GB 회수).

- 학습 loss: all 0.276 → 0.167, no_confusable 0.210 → 0.128. 제로샷 base는 한국어를 거의 못 봐(AUC 0.708) 학습 전엔 쓸모가 없었는데, 2 에폭으로 v2-m3 제로샷(568M)을 넘었다 — 쌍 AUC 0.823 → 0.922.
- **쌍 AUC와 질의 지표가 반대로 간 이유(all e2: AUC 최고인데 false no_match 최악).** false no_match는 "상위 5에 정답이 0~1건"인 질의에 몰린다(all e2: 정답 0건 4/10 · 1건 4/10 · 2건 1/6 · 3건 이상 0/31). 라벨이 "티켓 원인 == 정답 원인"이라 학습할수록 엄격해지고, 정답이 1건뿐이면 "5건 중 2 yes" 규칙에 걸린다. API 판정은 같은 설비·비슷한 증상 티켓도 yes라 0.014. 즉 학습 라벨(원인 일치)과 운영 판정(인용할 만큼 관련)이 다른 질문이다 — 다음 실험의 출발점.
- confusable 제외가 포함보다 나았다(e2 기준 0.070 vs 0.158). 카탈로그가 "헷갈림"으로 선언한 이웃 원인 쌍을 0으로 가르치면 모델이 이웃까지 버린다 — 정답이 1건뿐인 질의에서 그 이웃이 2번째 yes였다.
- 임계값이 0.005까지 내려간 것: sigmoid 출력이 0 근처에 몰려 있고(val 음성 중앙값 0.008), 양성은 0.995 — 분리가 커서 임계값 자체는 민감하지 않다.
