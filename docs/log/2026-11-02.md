## 결정
- 질문 원본 시각을 `OutboundEvent.asked_at`(tz-aware, 선택, 기본 None)으로 싣는다. 대안은 (a) Slack 어댑터가 inbound를 다시 조회(상태 생김), (b) reply_to를 질문 ts로 바꾸기(스레드 라우팅 깨짐). 필드 추가 + 기본 None이라 version 1 유지, 구버전 메시지도 읽힘(테스트로 확인). `inbound.reply()`가 `self.ts`를 복사하므로 파이프라인·워커는 손대지 않았다.
- BM25 토크나이저는 Kiwi + 태그 필터(NNG/NNP/SL, 단독 SN 제거) + 코드 정규식 선추출 + 카탈로그 사용자 사전(NNP). 대안은 (a) 공백/문자 n-gram(코드는 살지만 조사 붙은 명사가 다 다른 토큰이 됨), (b) bm25s 내장 영문 토크나이저(한글 불가).
- 사전 v1(188개, 카탈로그 단어 전부)은 v2(80개, 기본 Kiwi가 잘못 쪼개는 단어만 자동 검출: split/verb/neg_prefix/hyphen/extra)로 교체. 이유와 전체 목록은 docs/experiments/kiwi_dictionary.md. 숫자(SN)는 측정값 잡음이라 버린다 — 코드 안 숫자는 정규식 토큰에 있다.
- 코드 경계는 `\b`가 아니라 영숫자 lookaround. `\b`는 한글을 \w로 보기 때문에 "PECVD-03에서"에서 코드가 안 잡혔다(샘플 점검에서 발견).
- 하이브리드는 RRF(k=60), 벡터 top-20 + BM25 top-20 → top-5, 가중치 1:1 고정. 대안은 (a) 점수 정규화 후 가중합(cosine과 BM25의 스케일이 달라 정규화 방식 자체가 튜닝 대상), (b) 가중치 탐색(평가셋 170행에 맞추면 과적합). RRF는 순위만 쓰므로 스케일 문제가 없고 파라미터가 k 하나다. Hit.score는 RRF 값 그대로(2/61≈0.0328이 상한).
- 메타데이터 라우팅(`rag/query_parse.py` + `retrieve.filtered_search`)은 사전 매칭만(LLM 아님). 알람 코드(E-1101·e1101·E1101 정규화)가 있으면 alarm_code 일치로 후보를 제한하고 **BM25 순위만** 쓴다 — 코드 질의에서 벡터는 잡음(Step 2의 3/5). 코드로 걸리는 문서가 없으면(E-7777) 코드를 버리고 폴백. 설비 타입 키워드(PECVD/CVD, ETCH/에처/식각, PVD/스퍼터, PHOTO/포토/트랙/노광, CMP/연마)나 설비 ID(PECVD-03·pecvd03·CVD-07)가 하나 잡히면 equipment_type으로 제한한 hybrid. 타입 2개 이상(비교 질문)이면 필터 없음.
- 설비 ID는 **타입 단위**로만 제한한다(PECVD-03 → PECVD 전체). 같은 호기 이력만 보면 다른 호기의 같은 고장을 놓치고, 평가셋의 정답도 같은 cause의 다른 호기 티켓이다. ID 자체는 파싱해 두되(QueryFilters.equipment_ids) 필터엔 안 쓴다.
- Qdrant는 payload filter(MatchAny), BM25는 전체 점수 받아 사후 필터(318건이라 비용 없음).
- 답변 본체를 LangGraph StateGraph(`rag/graph.py`: retrieve → grade → generate | no_answer)로 교체. `pipeline.answer` 시그니처는 유지(search/chat 주입에 grade 추가), 계약·워커·어댑터 불변. 대안은 if/else 함수 체인 — 노드별 계측(timings·llm_calls)과 분기 추적(gate)을 state에 두는 편이 평가에 편하고, Step 4 이후 노드 추가(재질의·설비 되묻기)가 쉬워 LangGraph.
- grade 2단: (a) 벡터 top1 cosine < 0.50이면 LLM 없이 no_answer — positive 최저 0.535(Step 3 측정)보다 낮은 안전선. 코드 분기(BM25만)는 cosine이 없어 건너뛴다. (b) 상위 5건 각각 yes/no 판정(gpt-5-mini, 스레드 5 병렬), **yes 2건 미만이면 no_answer**. 처음엔 1건이면 통과였는데 negative 5건이 "소음·커넥터·냄새"처럼 느슨하게 겹치는 티켓 1건 때문에 답변됐고, positive는 yes 1건짜리가 0건이라 min_yes=2로 올렸다(positive 분포: yes 2건 7 · 3건 13 · 4건 28 · 5건 90). 평가셋으로 정한 값이라 과적합 위험은 적어 둔다 — 근거는 "5건 중 1건만 yes면 우연"이라는 원칙.
- generate 후검증: 인용 0건이면 no_answer. 전에는 본문에 "유사 이력 없음"이 있을 때만 no_match였다.
- no_answer 본문은 "유사 이력 없음"으로 **시작하지 않는다**: Slack 어댑터가 그 문구로 시작하는 본문을 버리고 자기 문구만 보내기 때문. status=no_match로 어댑터가 머리말을 붙이고 본문은 상세(판정 결과·참고 티켓 1건·신규 티켓 안내)만.
- Hit에 cosine 필드 추가. RRF 결과에서 벡터를 거친 문서는 cosine을 들고 다녀 grade·인용 점수·"참고(유사도)"에 쓴다. BM25 단독 결과는 None.
- `slack_reply` 지연 로그는 asked_at 우선, 없으면 reply_to(epoch) 폴백에 `(from reply_to)` 표시 — 2주차 664.9s 같은 값이 다시 나오면 구버전 메시지라는 뜻.

결과: **requeue는 통과, 재처리는 실패.** 브로커는 unacked를 돌려주지만 멱등 가드의 processing 키(STALE_PROCESSING_SEC=300)가 살아 있어 300초 안에 재시작한 워커는 그 메시지를 중복으로 ack한다 — 답이 조용히 사라진다. 300초 뒤 재시작이면 stale 판정으로 재처리된다(확인). 즉 drain 타임아웃 초과 시 답 유실 창이 최대 300초.
고치려면 drain 타임아웃 시 pending 태스크의 event_id에 대해 `guard.release()`를 부르고 연결을 닫으면 된다(워커 10줄). 2주차 "drain 120s 안에 끝나면 유실 0"은 그대로 참.

| bm25 | 46 | 0.435 [0.304, 0.587] | 0.543 [0.413, 0.696] | 0.484 [0.348, 0.625] | 21 |
| hybrid | 46 | 0.435 [0.283, 0.587] | 0.696 [0.565, 0.826] | 0.541 [0.413, 0.666] | 14 |

- 방향은 합성 티켓과 같다: R@5에서 hybrid(0.696) ≥ vector(0.63) > bm25(0.543), 실패도 hybrid 14 < vector 17 < bm25 21. R@1은 vector(0.5)가 hybrid(0.435)보다 높아 합성(hybrid 0.784 > vector 0.763)과 반대 — 단, n=46이라 95% CI가 전부 겹친다(폭 ±0.15). "같은 방향"은 R@5에서만 말할 수 있다.
- 합성 도메인과 다른 점 3줄:
  1. 사전 효과 0: 카탈로그가 없어 사용자 사전 없음. Kiwi가 영문을 단어별 SL로 넘기므로 is/on/when 같은 불용어가 다 토큰이 되고 어간 추출도 없다(`ignored`/`ignore` 다른 토큰) → BM25가 합성(사람 질의 0.947)과 달리 셋 중 꼴찌.
  2. 코드 토큰: 정규식(`[A-Z]+-\d+`)은 compose 이슈에서 거의 안 걸린다. 식별자는 소문자·밑줄(`depends_on` → depends + on), 버전(`v2.32.0`)은 W_SERIAL/SN이라 버려진다. 합성 도메인의 "코드가 보이면 BM25" 라우팅도 여기선 작동할 코드가 없다.
  3. 언어: bge-m3는 영문을 잘 다뤄 vector가 상대적으로 강하다(R@1 최고). 합성 도메인은 한국어 + 고정 어휘라 BM25가 유리했고, 여기선 중복 이슈가 서로 다른 말로 같은 버그를 쓰는 경우가 많아 임베딩이 유리하다.
- 미완: 미해석 중복 97건은 타임라인(cross-referenced) 이벤트로 원본을 더 찾을 수 있다.

## 한 줄
- 오타는 임베딩이 삼키고 약어는 BM25가 받친다 — 둘이 겹칠 때(both30) 벡터만 0.962 → 0.924로 내려가고 하이브리드는 0.975를 지켰다. 하이브리드의 값은 평균 성능이 아니라 한쪽이 흔들릴 때의 바닥이다.
- "모른다"는 점수가 아니라 판정으로 말해야 했다: cosine 임계값은 negative 9할을 잡으려면 positive 1할을 버려야 하지만, 티켓별 yes/no 판정에 "5건 중 2건 이상"을 걸면 negative 0.968·positive 손실 0.014에 정답 유실 0이었다. 값은 지연 +4.7초.
- 메타데이터 필터는 "코드가 보이면 BM25만, 설비가 보이면 그 설비만"으로 코드 단독 질의를 5/5로 올렸지만(hybrid 3/5), 평가셋의 22%에만 걸리고 negative 분리에는 도움이 안 됐다 — 모른다고 말하는 건 여전히 LLM 판정이 해야 한다.
- RRF 1:1 하이브리드는 1위 적중을 올렸지만(R@1 0.763 → 0.784) 용어 없는 질문은 못 살렸고(paraphrase_hard 0.6 → 0.567), 코드 단독 질의는 BM25 단독(5/5)보다 못하다(3/5) — 섞는 비율을 튜닝하는 대신 "코드가 보이면 BM25, 아니면 벡터"처럼 질의 형태로 갈라야 한다.
- RRF 점수는 "모른다"의 근거가 못 된다: negative와 positive의 최대값이 똑같이 2/61이다. 임계값은 cosine으로, 판정은 LLM으로.
- graceful drain을 넘겨 강제 종료하면 큐는 메시지를 돌려주지만 멱등 가드가 그걸 "이미 처리 중"으로 보고 버렸다(유실 창 300s). at-least-once는 브로커 혼자 못 만들고 가드의 수명과 같이 설계해야 한다 — 버리는 순간 키를 놓게 해서 창을 0으로 닫았다.
