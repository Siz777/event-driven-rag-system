# 2026-11-02 — 3주차 Step 0 (워밍업) · Step 1 (Kiwi + BM25) · Step 2 (하이브리드 RRF)

## 결정
- 질문 원본 시각을 `OutboundEvent.asked_at`(tz-aware, 선택, 기본 None)으로 싣는다. 대안은 (a) Slack 어댑터가 inbound를 다시 조회(상태 생김), (b) reply_to를 질문 ts로 바꾸기(스레드 라우팅 깨짐). 필드 추가 + 기본 None이라 version 1 유지, 구버전 메시지도 읽힘(테스트로 확인). `inbound.reply()`가 `self.ts`를 복사하므로 파이프라인·워커는 손대지 않았다.
- BM25 토크나이저는 Kiwi + 태그 필터(NNG/NNP/SL, 단독 SN 제거) + 코드 정규식 선추출 + 카탈로그 사용자 사전(NNP). 대안은 (a) 공백/문자 n-gram(코드는 살지만 조사 붙은 명사가 다 다른 토큰이 됨), (b) bm25s 내장 영문 토크나이저(한글 불가).
- 사전 v1(188개, 카탈로그 단어 전부)은 v2(80개, 기본 Kiwi가 잘못 쪼개는 단어만 자동 검출: split/verb/neg_prefix/hyphen/extra)로 교체. 이유와 전체 목록은 docs/experiments/kiwi_dictionary.md. 숫자(SN)는 측정값 잡음이라 버린다 — 코드 안 숫자는 정규식 토큰에 있다.
- 코드 경계는 `\b`가 아니라 영숫자 lookaround. `\b`는 한글을 \w로 보기 때문에 "PECVD-03에서"에서 코드가 안 잡혔다(샘플 점검에서 발견).
- 하이브리드는 RRF(k=60), 벡터 top-20 + BM25 top-20 → top-5, 가중치 1:1 고정. 대안은 (a) 점수 정규화 후 가중합(cosine과 BM25의 스케일이 달라 정규화 방식 자체가 튜닝 대상), (b) 가중치 탐색(평가셋 170행에 맞추면 과적합). RRF는 순위만 쓰므로 스케일 문제가 없고 파라미터가 k 하나다. Hit.score는 RRF 값 그대로(2/61≈0.0328이 상한).
- `slack_reply` 지연 로그는 asked_at 우선, 없으면 reply_to(epoch) 폴백에 `(from reply_to)` 표시 — 2주차 664.9s 같은 값이 다시 나오면 구버전 메시지라는 뜻.

결과: **requeue는 통과, 재처리는 실패.** 브로커는 unacked를 돌려주지만 멱등 가드의 processing 키(STALE_PROCESSING_SEC=300)가 살아 있어 300초 안에 재시작한 워커는 그 메시지를 중복으로 ack한다 — 답이 조용히 사라진다. 300초 뒤 재시작이면 stale 판정으로 재처리된다(확인). 즉 drain 타임아웃 초과 시 답 유실 창이 최대 300초.
고치려면 drain 타임아웃 시 pending 태스크의 event_id에 대해 `guard.release()`를 부르고 연결을 닫으면 된다(워커 10줄). 2주차 "drain 120s 안에 끝나면 유실 0"은 그대로 참.

### 보완: 멱등 가드 × drain 타임아웃 틈, 유실 창 300s → 0

## 한 줄
- RRF 1:1 하이브리드는 1위 적중을 올렸지만(R@1 0.763 → 0.784) 용어 없는 질문은 못 살렸고(paraphrase_hard 0.6 → 0.567), 코드 단독 질의는 BM25 단독(5/5)보다 못하다(3/5) — 섞는 비율을 튜닝하는 대신 "코드가 보이면 BM25, 아니면 벡터"처럼 질의 형태로 갈라야 한다.
- RRF 점수는 "모른다"의 근거가 못 된다: negative와 positive의 최대값이 똑같이 2/61이다. 임계값은 cosine으로, 판정은 LLM으로.
- graceful drain을 넘겨 강제 종료하면 큐는 메시지를 돌려주지만 멱등 가드가 그걸 "이미 처리 중"으로 보고 버렸다(유실 창 300s). at-least-once는 브로커 혼자 못 만들고 가드의 수명과 같이 설계해야 한다 — 버리는 순간 키를 놓게 해서 창을 0으로 닫았다.
