# 2026-11-02 — 3주차 Step 0 (워밍업) · Step 1 (Kiwi + BM25)

## 결정
- 질문 원본 시각을 `OutboundEvent.asked_at`(tz-aware, 선택, 기본 None)으로 싣는다. 대안은 (a) Slack 어댑터가 inbound를 다시 조회(상태 생김), (b) reply_to를 질문 ts로 바꾸기(스레드 라우팅 깨짐). 필드 추가 + 기본 None이라 version 1 유지, 구버전 메시지도 읽힘(테스트로 확인). `inbound.reply()`가 `self.ts`를 복사하므로 파이프라인·워커는 손대지 않았다.
- `slack_reply` 지연 로그는 asked_at 우선, 없으면 reply_to(epoch) 폴백에 `(from reply_to)` 표시 — 2주차 664.9s 같은 값이 다시 나오면 구버전 메시지라는 뜻.

## 실험 — drain 타임아웃 초과 (2주차 미실험, 호스트 워커 · 실제 LLM · 로컬 compose rabbitmq/redis/qdrant)
설정: `WORKER_DRAIN_TIMEOUT=5 REDIS_URL=redis://localhost:6379/0 python -m worker.main`, 질문 1건(Ev-drain-1) publish, `processing` 4초 뒤 SIGTERM.
```

12:20:49,381 signal SIGTERM received: stop requested
12:20:49,384 draining 1 in-flight (timeout 5s)…
12:20:54,385 WARNING drain timeout: 1 message(s) left unacked — broker will requeue on disconnect
12:20:54,390 connection closed. processed=0 failed=0 duplicates=0
(프로세스 종료 12:21:04 — to_thread의 LLM 호출이 끝날 때까지 10초 더 살아 있음. ai_results publish는 없음)
관리 API: ai_tasks messages 1 unacked 0  ← requeue 확인. ai_results 0. Redis idem:Ev-drain-1 = processing:1793589645
```
워커 재시작(40초 뒤):
```
12:21:24,995 consuming ai_tasks … idempotency redis
12:21:25,002 duplicate, ack only: Ev-drain-1      ← 재처리 안 됨. ai_tasks 0, ai_results 0
```
키를 400초 전 processing으로 바꾸고 같은 event_id 재발행:
```
12:21:46,509 WARNING stale processing key for Ev-drain-1 (402s old): reprocessing
12:22:05,030 done Ev-drain-1 → ai_results status=answered citations=5 (18.5s)
```
결과: **requeue는 통과, 재처리는 실패.** 브로커는 unacked를 돌려주지만 멱등 가드의 processing 키(STALE_PROCESSING_SEC=300)가 살아 있어 300초 안에 재시작한 워커는 그 메시지를 중복으로 ack한다 — 답이 조용히 사라진다. 300초 뒤 재시작이면 stale 판정으로 재처리된다(확인). 즉 drain 타임아웃 초과 시 답 유실 창이 최대 300초.
고치려면 drain 타임아웃 시 pending 태스크의 event_id에 대해 `guard.release()`를 부르고 연결을 닫으면 된다(워커 10줄). 이번 주 범위 밖(워커 불변)이라 기록만. 2주차 "drain 120s 안에 끝나면 유실 0"은 그대로 참.
