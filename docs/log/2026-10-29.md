- 이벤트 계약(2주차 Step 1): event_id는 생산자가 정하고 기본값 없음 — 서버가 uuid를 만들면 재전송마다 다른 키가 되어 멱등 가드(Step 5)가 무의미. OutboundEvent에 channel·reply_to를 복사해 둠 — 답 보내는 쪽이 inbound를 조회하지 않아야 상태 없이 재시작 가능. ts는 tz-aware만 허용, 모르는 필드·version 거부(extra="forbid", Literal[1]).

- 웹훅(2주차 Step 2): POST /events는 Slack Events API 전용. 서명 실패·5분 밖 타임스탬프는 401, JSON 깨짐 400, InboundEvent 검증 실패는 200 ignored + WARNING 로그(422면 Slack이 재전송), publish 예외 503, 처리 대상 아닌 이벤트(봇 글·편집·채널 일반 메시지·미지 타입)는 200 ignored — Slack은 2xx가 아니면 재전송하므로 "무시"도 2xx로 답한다. source는 Literal 대신 비어 있지 않은 str로 완화(어댑터 등록 검증은 라우터 몫). 처리 대상은 app_mention + DM(message, channel_type=im)만.

- 큐 토폴로지(2주차 Step 3): 재시도는 브로커 자동 requeue가 아니라 워커가 x-retry-count를 올려 TTL 큐 3단(5s/25s/125s)으로 보내는 방식. 즉시 requeue는 같은 실패를 초당 수십 번 반복하고(LLM 호출이면 비용), 횟수도 셀 수 없다. ai_tasks의 DLX는 워커가 손도 못 댄 경우의 안전망으로만. 패키지명은 `queue` 대신 `mq` — `queue`는 stdlib 모듈이라 cwd의 같은 이름 패키지가 가린다(확인: `python -c "import queue; print(queue.__file__)"`가 로컬 경로를 찍음).

- 워커(2주차 Step 4): 재시도는 워커가 x-retry-count를 올려 TTL 큐로 publish 후 원본 ack. nack(requeue=True) 안 씀. 파이프라인은 to_thread — 동기 LLM 호출로 이벤트 루프를 막으면 AMQP heartbeat가 끊겨 연결이 죽는다. chat()의 내부 재시도는 2회로 제한(간격·횟수는 큐가 담당). 인용 파싱은 `[INC-a, INC-b]` 묶음 인용 때문에 대괄호가 아니라 ID 패턴(`INC-\d{4}-\d{4}`)으로 — 첫 수동 실행에서 5건 인용이 1건으로 잡힌 걸 보고 고침.

- 멱등성(2주차 Step 5): SETNX vs DB unique — 키 하나에 TTL이 필요하고(24h 뒤 잊어도 됨) 조회가 처리 경로마다 1회라 Redis SET NX EX. DB unique는 테이블·마이그레이션·정리 작업이 생기고, 지금 시스템에 DB가 없다. 가드는 소비 지점(워커)에만 — 웹훅 앞에서 거르면 publish 실패 재전송과 구분이 안 돼 질문이 유실된다. Redis 장애 시 가드 OFF로 계속 처리(중복 답 < 무응답). 처리 중 죽은 경우는 processing:{epoch} 값의 나이(300s)로 판정 — 두 번째 키·짧은 TTL 대신 값 하나에 상태와 시각을 넣는 쪽이 원자적이고 단순.

- Docker(2주차 Step 6): 워커 CMD는 exec form + `init: true`(tini). shell form이면 PID 1이 sh라 SIGTERM이 python에 안 가고 stop_grace_period 뒤 SIGKILL → 처리 중 답 유실. 모델 가중치·데이터는 볼륨 — 이미지는 코드만(288KB), 재빌드가 pip 캐시에만 걸린다. api 이미지는 별도 requirements-api.txt(267MB) — torch를 웹훅에 싣지 않는다. torch는 CPU 휠(`--index-url …/whl/cpu`) 고정 — PyPI aarch64 기본 휠이 nvidia-* 3.3GB + triton 0.9GB를 끌고 와 10.2GB가 됐다.

- Slack Socket Mode(2주차 Step 7): 웹훅 대신 WebSocket — 공개 URL·ngrok 없이 로컬·compose에서 바로 돈다. `to_inbound`는 웹훅 것을 재사용(source만 slack_socket). 계약 수정 2개: (1) `reply_to`는 새 질문이면 메시지 ts — 전엔 null이라 OutboundEvent.reply_to가 event_id("Ev…")로 채워져 chat.postMessage thread_ts에 못 쓴다. 이 값은 epoch라 답글 소비자가 질문→답 왕복 시간을 그 자리에서 잰다. (2) status에 progress 추가 — "검색 중…"은 큐를 거치지 않고 어댑터가 say로 직접(큐를 거치면 워커가 LLM 전에 publish해야 하고, 그 순서 보장이 복잡). 답글 ack는 전송 성공 뒤에만, 영구 오류(channel_not_found 등)는 폐기·일시 오류는 nack requeue. publish 실패는 웹훅과 달리 재전송이 없어 질문이 유실 — 사용자에게 한 줄 알리고 단순하게 둔다.
