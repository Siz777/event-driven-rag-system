# Step 12 — 임베딩 모델 비교 (검색 단독, 2026-11-20)

목적은 "임베딩 선택이 검색 성능에 얼마나 영향을 주는가"를 같은 조건에서 재는 것이고, 새 모델 채택이 아니다. 판정 기준은 사전에 정한 ±0.03 — 그 안이면 "차이 없음".

## 조건
- 후보: `BAAI/bge-m3`(기준) · `Qwen/Qwen3-Embedding-0.6B` · `nlpai-lab/KURE-v1`. 셋 다 1024차원, 문서는 청킹 없이 티켓 1건 = 벡터 1개(doc_text=full, 318건, 문서 토큰 최대 427 / Qwen 토크나이저로 564).
- 바꾼 것은 벡터 컬렉션뿐: `manufacturing_baai_bge_m3_v1`(기존, 안 건드림) · `manufacturing_qwen_qwen3_embedding_0_6b_v1` · `manufacturing_nlpai_lab_kure_v1_v1`. BM25 색인·Kiwi 사전·메타데이터 필터·RRF(k=60, 1:1)는 그대로.
- Qwen3만 질의에 instruction을 붙였다(문서에는 안 붙임): `Instruct: Given a query, retrieve relevant incident tickets\nQuery: `. bge-m3·KURE-v1은 프롬프트 없음. `experiments.jsonl` 각 행의 `query_prompt`에 기록.
- 디바이스는 셋 다 MPS(sentence-transformers 자동 선택, CPU 폴백 없음), 배치 32.
- 평가는 `rag.eval`만(graph·cross-encoder·cosine 안전선 없음), 283행 셋, k=5, method 2개(vector, hybrid+filter). 실행: `EMBED_MODEL=<모델> python -m scripts.eval_embed index|eval`, 표는 `python -m scripts.eval_embed report`. 행별 top-5는 `domains/manufacturing/eval/embed_compare/<slug>.json`.
- 각 설정 1회 실행(검색은 결정적). 기준 행은 오늘 다시 돌렸고 11-02 기록과 일치한다(124행 vector 0.444 / 0.637 / 0.523, hybrid+filter 0.492 / 0.75 / 0.579).

## 결론
임베딩을 바꿔도 파이프라인이 실제로 쓰는 숫자(hybrid+filter R@5, 124행)는 0.750 / 0.750 / 0.734로 ±0.03 안 — **차이 없음**. ±0.03을 넘은 칸은 Qwen3-0.6B의 세 곳(124행 vector R@5 +0.040, hybrid+filter R@1 +0.040 · MRR +0.035)인데, 같은 모델이 170행 vector에서는 R@1 −0.036 · MRR −0.054로 반대 방향이고, 질의 단위로 보면 15 대 10(vector R@5) · 7 대 2(hybrid+filter R@1)라 부호 검정으로 우연과 구분되지 않는다(양측 p ≈ 0.42, 0.18). 득실은 원인 묶음 간 교환(히터·E-1301 ↔ 펌프 진동·E-5201)이고, 세 모델이 공통으로 틀리는 30 ~ 39건(설비 없이는 미결정인 증상, confusable 이웃)이 실패의 본체다 — 124행의 한계는 임베딩이 아니라 질의에 없는 정보 쪽에 있다는 11-03 분석과 같은 결론이다. negative 분리도 그대로다(max 0.614 ~ 0.640, 안전선 0.50 재조정 불필요, LLM 판정 필수). Qwen3-0.6B는 색인이 2.6배 느리다. 한계: 평가셋 한 벌·1회 실행, Qwen3 instruction은 영어 한 문구만 시도했고(문구를 튜닝하지 않음), 모델 채택 여부는 이 문서의 범위가 아니다.
